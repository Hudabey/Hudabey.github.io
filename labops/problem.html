LabOps a relational DBMS for GPU research ops
02 · Requirements analysis

One lab. Six researchers. Hundreds of runs.

The lab owns no hardware — it rents H100, A100 and RTX-4090-class nodes by the hour from RunPod, Lambda, Vast.ai and CoreWeave. Every project advances through experiment runs: a researcher occupies a node for a bounded time, the run produces named metrics and checkpoints, and its outcome bears on the falsifiable claims the project tracks.

Goal 1

Cost visibility

GPU rental is the dominant cost. Spend must be attributable per project, per node type, per time window — impossible when run logs live in scattered notebooks.

Goal 2

Reproducibility

Every metric and checkpoint must be traceable to the exact run, node, and researcher that produced it.

Goal 3

Scientific accounting

Claims are the unit of research progress. Which runs support claim C5? Which claims are still open, and what would close them?

Goal 4

Auditability

Run status changes (RUNNING → GREEN/FAILED) must leave a trace no user can forget to write.

Users

Lab lead — approves budgets, reads the per-project dashboard, tracks claim verdicts.

Researchers (PhD/MSc) — register runs, record metrics and checkpoints, link runs to claims.

Research engineer — manages node inventory and pricing, investigates failed runs, maintains the audit trail.

Business rules → the schema will enforce them

· A project has exactly one lead; a run belongs to exactly one project, node, and researcher.

· A metric name appears once per run (composite uniqueness).

· Runs ↔ claims is many-to-many, resolved by an associative entity that also stores the evidence note.

· Training runs need ≥ 40 GB VRAM — enforced by a stored procedure.

· Every status change is recorded automatically — enforced by a trigger.

The thesis  Push the business rules into the database engine itself — constraints, a trigger, a transactional procedure — rather than trusting application code. Rules in the engine are unforgeable.
